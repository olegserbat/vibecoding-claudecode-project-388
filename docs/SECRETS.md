# Куда класть секретные токены

Работа над проектом идёт в **облачном окружении** Claude Code (сессия
поднимается в одноразовом контейнере Anthropic, репозиторий клонируется туда
заново). Это меняет правила по сравнению с локальной разработкой.

## Главное про облако

- **Контейнер эфемерный.** Файл `.env`, созданный внутри сессии, исчезает
  вместе с контейнером. Хранить секреты в файлах проекта бессмысленно и опасно.
- **Секреты живут в настройках окружения**, а не в репозитории. Они
  подставляются в контейнер как обычные переменные окружения при старте сессии.
- **Не присылать токен текстом в чат.** Сообщение попадает в историю сессии.
  Если токен уже был отправлен в переписку — его нужно отозвать и выпустить заново.

## 1. Основной способ: переменные окружения самого окружения

В интерфейсе Claude Code (веб `claude.ai/code` или десктоп-приложение) окружение
настраивается отдельно от репозитория: список окружений → нужное окружение
(здесь это **MarketPlace**) → его настройки → раздел переменных окружения
(Environment variables / Secrets). Там задаётся пара «имя → значение».

Значение хранится на стороне Anthropic, в git не попадает, и доступно каждой
новой сессии этого окружения как обычная переменная:

```bash
echo "$MY_API_TOKEN"        # в bash внутри сессии
```

```python
import os
token = os.environ["MY_API_TOKEN"]   # в коде
```

Проверить, что переменная доехала до сессии, не раскрывая значение:

```bash
env | cut -d= -f1 | grep MY_API_TOKEN     # видно только имя
```

Переменные задаются **на окружение**, поэтому разные окружения (например
`Default` и `MarketPlace`) могут иметь разные наборы токенов, и секрет из одного
не виден сессиям другого.

## 2. Для GitHub персональный токен, как правило, не нужен

Сессия уже авторизована в GitHub: доступ идёт через GitHub MCP и git-прокси, под
учётной записью, привязанной к Claude Code. Скилу `tracker`, который коммитит
прогоны в `olegserbat/tracker-data`, собственный PAT не требуется — нужно лишь,
чтобы этот репозиторий был доступен сессии (добавлен в её список репозиториев /
разрешён в настройках GitHub-доступа Claude).

Класть свой PAT в переменные окружения стоит только если нужен доступ мимо этого
механизма — например к чужой организации, не подключённой к Claude.

## 3. Для GitHub Actions: Secrets репозитория

CI выполняется на стороне GitHub, а не в облачной сессии, поэтому у него своё
хранилище: `Settings → Secrets and variables → Actions → New repository secret`.
В workflow значение подставляется как `${{ secrets.ИМЯ }}` — так уже сделано с
`HEXLET_ID` в `.github/workflows/hexlet-check.yml`.

## 4. Важное ограничение: сетевая политика окружения

У окружения есть политика исходящего трафика, и она может быть строже, чем
кажется: в текущем окружении часть внешних доменов режется прокси (проверено —
`docs.claude.com` и `code.claude.com` возвращают `EGRESS_BLOCKED`).

Отсюда практическое следствие: **токен к внешнему API бесполезен, если домен
этого API не разрешён политикой окружения**. Прежде чем заводить секрет для
стороннего сервиса, стоит проверить доступность домена и при необходимости
поменять сетевую политику окружения в его настройках. Обходить проверку
сертификатов или отключать прокси нельзя.

## Зачем тогда `.gitignore` и `.env`

`.gitignore` в корне остаётся нужен как страховка, а не как способ хранения:
в облачной сессии агент делает коммиты и пуш от вашего имени, и любой файл с
секретом, случайно оказавшийся в рабочей директории, иначе рискует попасть в
коммит. Правила закрывают `.env*`, `secrets/`, `*.key`, `*.pem`,
`credentials.json` и локальные настройки Claude.

Файл `.env` при этом остаётся рабочим вариантом для локального запуска на своей
машине (`cp .env.example .env`), если проект когда-то будет запускаться вне
облака. В облачной сессии он не нужен: там источник значений — настройки
окружения.

## Чего делать нельзя

- Писать реальный токен в `.env.example`, `README.md`, файлы скилов
  (`.claude/skills/**`) или в текст задачи — всё это коммитится.
- Присылать токен сообщением в чат сессии.
- «Спрятать» токен, добавив файл в `.gitignore` уже **после** коммита:
  `.gitignore` не действует на файлы, уже попавшие под контроль версий. Такой
  токен считается скомпрометированным — отозвать, выпустить заново, а файл
  убрать из индекса (`git rm --cached <файл>`).
