# tracker

Обход списка URL и сборка единой таблицы цен: одна строка на товар.
Цену для каждого URL достаёт не сам tracker, а скил `extract-price` —
tracker только организует обход, накопление строк, сравнение с прошлым
прогоном, отправку сводки и сохранение результата в репозиторий истории.

Наружу tracker выдаёт **изменения, а не прайс-лист**: собранная таблица
нужна для сравнения и для хранения, а пользователю показывается то, что
изменилось с прошлого прогона.

## Когда использовать

- «Собери таблицу цен по этим ссылкам»
- «Пройдись по списку URL и выпиши цены»
- «Сравни цены по всем товарам из списка»
- «Сделай прогон цен / прайс-лист по этим карточкам»
- «Проверь, где есть скидка и рассрочка» (по нескольким ссылкам)

Для **одного** URL этот скил не нужен — там достаточно `extract-price`.

## Вход

Список URL карточек товаров. Источник списка, по приоритету:

1. URL, которые пользователь дал в запросе;
2. файл/таблица, на которые он указал;
3. список по умолчанию (ниже), если пользователь просит «прогнать
   обычный список» или не даёт свой.

### Список по умолчанию

```
https://dr-coffee.su/catalog/kofemashiny-proxima/f10/
https://dr-coffee.su/catalog/kofemashiny-proxima/btb-101-6/
https://dr-coffee.su/catalog/kofemashiny-proxima/btb-101-3/
https://dr-coffee.su/catalog/kofemashiny-proxima/btb-102/
https://dr-coffee.su/catalog/kofemashiny-proxima/m12-plus/
```

Перед прогоном убрать дубликаты URL, сохранив порядок первого появления.

## Что делать

### 1. Обойти список по одному URL

Для каждого URL из списка, строго последовательно, сверху вниз:

1. Вызвать скил **`extract-price`** для этого URL.
2. Получить от него объект `{name, regular_price, sale_price, has_credit}`.
3. Добавить в таблицу одну строку: `URL` из списка + поля из объекта.

Логику парсинга не дублировать и не переписывать: правила поиска цены,
различения обычной и скидочной цены, определения рассрочки и
нормализации чисел живут в `extract-price` — tracker их только
использует. Если нужно поменять то, как достаётся цена, — правится
`extract-price`, а не этот скил.

Темп запросов задаёт `extract-price` (пауза 2–5 секунд между запросами
к одному домену, никаких пачек и параллельных запросов). При обходе
списка эту паузу выдерживать между соседними URL: список идёт
последовательно, а не в несколько потоков.

### 2. Обработать неудачные URL

Прогон не останавливается из-за одной страницы. Если по URL цену
получить не удалось (страница не открылась, товара нет, цены на
странице нет):

- строка в таблице всё равно создаётся;
- `name` — если удалось определить, иначе `null`;
- `regular_price` и `sale_price` — `null`;
- `has_credit` — `false`, если страница загрузилась и признаков
  рассрочки нет; `null`, если страницу вообще не удалось прочитать.

Ничего не выдумывать и не подставлять цену «по аналогии» с соседним
товаром.

### 3. Собрать таблицу прогона

Одна строка на товар, порядок строк — как в исходном списке. Колонки
строго в этом порядке:

| URL | name | regular_price | sale_price | has_credit |
|---|---|---|---|---|

- `URL` — ссылка из списка, ровно в том виде, в каком она была дана.
- `name`, `regular_price`, `sale_price`, `has_credit` — как их вернул
  `extract-price`, без пересчёта и переформатирования.
- Цены — числа с двумя знаками после точки (`129990.00`), пустое
  значение — `null`.
- `has_credit` — `true` / `false` (или `null` для непрочитанной
  страницы).

Эта таблица — рабочий результат: она идёт на сравнение (шаг 5) и в
репозиторий (шаг 8). **Целиком пользователю её не выводить** — кроме
первого прогона, когда сравнивать не с чем, и случая, когда сырые цены
попросили явно («покажи таблицу», «дай все цены», просьба о CSV/JSON).

### 4. Найти предыдущий прогон

**До** сохранения нового прогона (иначе он сам окажется последним):

1. Получить список файлов в корне `olegserbat/tracker-data` через
   GitHub MCP (`get_file_contents` с путём `/`).
2. Отобрать файлы вида `YYYY-MM-DD.json`, всё прочее (README и т.п.)
   игнорировать.
3. Взять файл с **максимальной датой** в имени — это предыдущий
   прогон. Дата берётся из имени файла, а не из даты коммита.
4. Прочитать его содержимое и разобрать как массив строк прогона.

Частные случаи:

- **Подходящих файлов нет** — это первый запуск, сравнивать не с чем.
  Шаг 5 пропустить, сказать об этом одной строкой и показать таблицу
  прогона целиком.
- **Последний по дате файл — сегодняшний** (повторный прогон в тот же
  день): это и есть предыдущий прогон, сравнивать с ним. Он же будет
  перезаписан на шаге 8.
- **Файл не читается или содержит не тот формат** — не гадать: сказать
  об этом, показать таблицу целиком и перейти к сохранению.

### 5. Сравнить прогоны и выдать значимые изменения

Сравнить предыдущий прогон (шаг 4) с текущим (шаг 3), сопоставив товары
**по `url`** и сравнив по каждому поля `regular_price`, `sale_price`,
`has_credit`.

Что считать значимым и как это выводить — задано в
[`KNOWLEDGE.md`](../../../KNOWLEDGE.md); файл лежит в корне репозитория
проекта, рядом с `send.py`. Прочитать его перед сравнением и следовать
ему; пороги и формулировки не придумывать заново. Кратко, чтобы не
расходилось:

- `regular_price` — изменение строго больше 1%;
- `sale_price` — изменение строго больше 5%, если скидка была в обоих
  прогонах, плюс всегда — появление и исчезновение скидки;
- `has_credit` — только смена состояния;
- исчезнувшие товары — отдельным блоком.

На выходе — **список только значимых изменений**. Ни таблицы, ни
неизменившихся строк, ни изменений в пределах порогов. Если не
сработало ни одно правило — одна строка о том, что значимых изменений
между прогонами нет.

### 6. Получить текст у diffWriter и отправить через send.py

Текст сообщения пишет не сам tracker, а субагент **`diffWriter`**
(модель Haiku, определён в `.claude/agents/diffWriter.md`). tracker
передаёт ему готовый анализ и правила оформления, получает обратно
короткий текст и отдаёт этот текст в `send.py`.

```
шаг 5: diff (значимые изменения)
   ↓ diff + правила оформления
diffWriter → короткий текст
   ↓
python3 send.py "<текст>"
```

**Что передавать в diffWriter:**

1. **Diff из шага 5** — уже отобранные значимые изменения: товар, какое
   поле изменилось, было и стало, посчитанный процент. Отдельно —
   исчезнувшие и недоступные товары. Сырую таблицу прогона не
   передавать: агент пишет по diff, а не по ценам.
2. **Правила оформления** — блок «Формат сводки» ниже, текстом.

Сравнение и арифметику агенту не отдавать: пороги и проценты
считает tracker на шаге 5, diffWriter только формулирует.

**Формат сводки** (эти правила и передаются агенту):

- **Одна строка на одно изменение**, в том же порядке, что и список из
  шага 5. Если у товара сработало два правила — это две строки.
- Строка пишется словами, а не полями объекта: название товара, что
  произошло, было → стало, процент в скобках. Без JSON, таблиц,
  markdown-разметки и URL — сводка читается в мессенджере, а не в
  терминале.
- Проценты и цены — как в `KNOWLEDGE.md`: процент до одного знака,
  цены как в файлах прогона.

Примеры строк:

```
Proxima BTB 101+6: подорожала 60 000 → 77 270 (+28.8%)
Proxima BTB 102: скидка исчезла (была 82 875)
Dr.coffee F10: появилась рассрочка
Proxima M12 Plus: товар пропал из каталога
```

**Если значимых изменений нет** — отправлять ровно одну строку:

```
Значимых изменений цен нет
```

Тишина не годится: сводка уходит на каждом прогоне, даже когда менять
нечего — так видно, что прогон состоялся.

**Как отправлять:**

Отправляется ровно тот текст, который вернул `diffWriter`, без правок
и без добавлений от себя. `send.py` лежит в корне репозитория проекта и шлёт текст в Telegram
через Bot API. Вызов — ровно один аргумент:

```
python3 send.py "<текст сводки>"
```

- Один прогон — **одно** сообщение: все строки в одном тексте,
  разделённые переводом строки. Не слать по сообщению на изменение.
- Текст уходит как есть, без `parse_mode`, поэтому markdown-разметка в
  сводке бессмысленна: `*`, `_` и обратные кавычки придут символами.
- Скрипту нужны переменные окружения `TELEGRAM_BOT_TOKEN` и
  `TELEGRAM_CHAT_ID`. Их значения не подставлять в командную строку и
  не выводить в ответ.
- Отправлять после сравнения и до сохранения — как здесь и стоит.

**Если `diffWriter` недоступен или вернул пустой ответ** — не бросать
шаг: собрать текст по тем же правилам самому и отправить его, отметив
одной строкой, что агент не отработал.

**Если отправить не удалось** — сводку не терять: показать её
пользователю и одной строкой сказать, что отправка не прошла и почему.
Скрипт объясняет причину сам: код `2` — не заданы переменные окружения
или пустой текст, код `1` — ошибка Telegram API или сети. Не подменять
другим каналом связи, не повторять отправку вслепую и не пропускать
из-за этого шаг 8.

### 7. Подвести итог прогона

Одна–три строки: сколько URL обошли, по скольким цена получена, по
каким не получена и почему, с какой датой сравнивали.

### 8. Сохранить прогон в репозиторий tracker-data

После сравнения закоммитить таблицу через **GitHub MCP** (инструменты
`mcp__github__*`, при необходимости подгрузить их через ToolSearch).

**Схема хранения: один прогон — один файл.**

- Репозиторий: `olegserbat/tracker-data`, ветка по умолчанию.
- Путь: корень репозитория, имя файла — дата прогона в формате
  `YYYY-MM-DD.json` (например, `2026-08-23.json`). Никаких подпапок.
- Содержимое: та же таблица прогона из шага 3, в JSON — массив
  объектов, один объект на строку таблицы, порядок как в таблице:

```json
[
  {
    "url": "https://example.com/product/",
    "name": "Название товара",
    "regular_price": 129990.00,
    "sale_price": 119990.00,
    "has_credit": true
  }
]
```

- Ключи ровно эти пять и в этом порядке. Значения — те же, что в
  таблице: цены числами (или `null`), `has_credit` булево (или `null`).
- Никаких обёрток и метаполей вокруг массива (ни `rows`, ни `date`, ни
  `count`) — дата уже в имени файла.

Порядок действий:

1. Файла с этой датой нет — создать (`create_or_update_file`). Есть —
   перезаписать результатом нового прогона, передав `sha`
   существующего файла: один прогон за дату, повторный прогон в тот же
   день заменяет файл, а не добавляется рядом. Список файлов и `sha`
   уже получены на шаге 4 — повторно их запрашивать не нужно.
2. Сообщение коммита — короткое и однотипное, например
   `Tracker run 2026-08-23`.

Если репозитория нет в области доступа сессии — добавить его
(`list_repos` → `add_repo`), а не коммитить куда-то ещё. Это же
касается шага 4: без доступа к репозиторию не будет и предыдущего
прогона. Если доступ получить не удалось: таблицу всё равно показать
пользователю, а про несравнённый и несохранённый прогон сказать одной
строкой — молча пропускать шаги нельзя.

## Ограничения / что не делать

- Не парсить страницы самостоятельно в обход `extract-price` и не
  копировать его правила внутрь этого скила.
- Не обходить список параллельно и не слать запросы пачками.
- Не добавлять в таблицу колонки сверх пяти перечисленных (ни валюту,
  ни скидку в процентах, ни дату) — пока пользователь не попросит явно.
- Не выводить прайс-лист вместо списка изменений и не пересказывать
  неизменившиеся строки: сырые цены целиком — только на первом прогоне
  или по явной просьбе.
- Не задавать пороги значимости «на глаз»: они живут в `KNOWLEDGE.md`.
- Не искать предыдущий прогон после сохранения нового — иначе им
  окажется только что записанный файл.
- Не отправлять через `send.py` таблицу целиком, сырые цифры или
  неизменившиеся строки — только сводку по значимым изменениям.
- Не отдавать `diffWriter` сравнение прогонов и подсчёт процентов: он
  пишет текст по готовому diff, а считает tracker.
- Не переписывать текст, который вернул `diffWriter`, перед отправкой.
- Не молчать в канал, когда изменений нет: уходит строка «Значимых
  изменений цен нет».
- Не прерывать прогон на первой ошибке и не выбрасывать проблемные URL
  из таблицы.
- Не переходить по ссылкам на другие товары со страницы: обходятся
  ровно те URL, что в списке.
- Не коммитить прогон в другой репозиторий, не в корень или под другим
  именем: только `olegserbat/tracker-data`, только `YYYY-MM-DD.json`.
- Не дописывать новый прогон в файл прошлой даты и не складывать
  несколько прогонов в один файл.
- Не сравнивать с файлом, выбранным по дате коммита или по порядку в
  листинге: предыдущий прогон определяется датой в имени файла.
